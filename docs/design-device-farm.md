# 설계: 빌드 점검

## 목표

새 빌드가 나오면 사람이 기기를 들지 않아도 연결된 실기기 전부에서 주요 화면이 열리는지, 확정한 플로우가 도는지를 본다. 판정은 규칙으로만 한다(LLM은 후보를 만들 때만 쓴다).

## 실행 단위

```
점검(run) ─ 기기(outcome) ×N ─ 화면(screen) ×M
```

1. **설치**: 플랫폼·빌드 종류별 설치 방식(`install.sources`)으로 빌드를 깔고 앱을 연다. 실패하면 그 기기는 `install_failed`.
2. **고정 화면**: `scenarios`에서 `excludedScenarioPaths`를 뺀 화면을 딥링크로 연다. 경로가 맞고 문서가 다 읽히고 글자나 이미지가 있고 잠시 뒤에도 그대로일 때까지 기다린 뒤 판정한다.
3. **플로우**: 사람이 확정한 플로우를 홈부터 스텝 순서로 돈다.
4. **데이터 QA**: `qa.screens`가 있고 API 주소가 있으면 돈다.
5. **정책 대조**: 뽑힌 정책 규칙이 걸린 화면이 있으면 돈다.

기기 두 대씩 동시에 돈다. 점검 중인 기기는 봇 잠금이 걸리고, 사람이 조작 잠금을 쥔 기기는 건너뛴다. 「점검 멈추기」는 도는 화면·플로우 하나가 끝나면 멈춘다.

## 화면 판정

| 상태 | 뜻 |
| --- | --- |
| passed | 기준 화면과 같다 |
| candidate | 기준 화면이 없다. 사람이 「기준 화면」 탭에서 확정한다 |
| failed | 앱 오류 문구(`appErrorText`), 그려지지 않음, 기준과 픽셀 차이(채널 오차 16 넘는 픽셀이 2% 넘음) |
| login_required | `loginPaths`로 튕겼다. 계정 세션을 다시 잡아야 한다 |

기준 화면은 기기 모델·시나리오별로 둔다. 상태바는 시각·배터리가 바뀌므로 잘라 내고 비교한다.

실패한 화면은 묶음(스크린샷, 기준·차이 PNG, 그 기기의 콘솔·네트워크·시스템 로그, 직전 영상)을 남긴다.

## 버튼 눌러보기와 화면 지도

점검을 켤 때 「버튼 눌러보기」를 고르면 정상으로 열린 화면의 버튼·링크를 하나씩 눌러 본다(화면당 12개, 금지어·뒤로·하단 탭 제외).

- 반응: 경로가 바뀌었거나 화면 내용(글자·대화상자 수)이 바뀌었다. 바뀐 뒤의 제목·팝업 문구를 남긴다.
- 반응 없음 / 오류(앱 오류·크래시·네트워크·로그인 튕김) / 건너뜀.
- 쓰기 요청은 탐색과 같은 허용 목록 가드로 막는다. 가드를 못 걸면(iOS) 누르지 않는다.

결과는 화면 지도(`test-results/screen-map.json`)에 간선으로 쌓인다: `from 화면 --누른 버튼--> to 화면 / 팝업 / 반응 없음`. 지도는 플로우를 조립하는 재료가 된다.

## 플로우

플로우는 `home` 스텝에서 시작해 `click`(버튼·링크 이름)과 `expectText`(문구 확인)로만 이어진다. 주소로 화면을 여는 스텝은 없다. 실제 사용자처럼 눌러서만 간다.

후보를 만드는 길:

| 출처 | 방법 |
| --- | --- |
| ai_generated | 프론트 체크아웃(`FLOW_PRD_ROOT`)의 PRD 문서를 OpenAI 호환 LLM에 주고 후보를 받는다. 요구 문장은 PRD에 그대로 있어야 한다 |
| map_built | 화면 지도 위에서 블록을 이어 붙인다. 서버가 지도 위에서 다시 밟아 본다 |
| recorded | 사람(`npm run record`)이나 Claude(MCP)가 기기를 움직인 기록. 홈부터 다시 돌 수 없는 구간에서 끊는다 |

금지 버튼(`guard.forbiddenClickNames`)이 들어간 후보는 받지 않는다. 사람이 확정한 것만 점검에서 돈다.

## 새 빌드 자동 점검

5분마다 Firebase 릴리스·TestFlight 빌드를 본다. 새 version+build가 보이면 그 플랫폼의 연결된 기기로 자동 점검을 대기열에 넣는다. 수동 점검이 도는 중이면 끝난 뒤 바로 꺼낸다.
