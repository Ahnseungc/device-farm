# 설계: 카오스 탐색

## 목표

확정 플로우와 화면 점검은 정해진 길만 본다. 순서가 꼬일 때(팝업을 띄운 채 탭 이동, 로딩 중 뒤로) 깨지는 화면을 찾으려고, 봇이 Android dev 앱을 **가중치 무작위**로 돌아다니며 사람이 실수로 하는 동작을 섞는다. LLM과 학습 모델은 쓰지 않는다. 판정은 탐색 점검과 같은 규칙이고, 쓰기 요청 가드도 그대로 쓴다.

데이터 초기화가 없으므로 하루 한 번인 동작(출석·퀴즈)을 써 버린다. 플로우 점검 계정과 다른 **카오스 전용 계정**을 쓴다.

## 상태와 행동

상태는 경로와 열린 팝업 수다. 버튼 이름까지 넣으면 키패드 숫자·실시간 값만 바뀌어도 새 상태가 된다.

| 행동 | 내용 | 기본 가중치 |
| --- | --- | --- |
| press | 보이는 버튼·링크. 금지어·광고(`avoidedNamePattern`)·하단 탭 제외 | 1.0 |
| back | 화면 상단 뒤로 버튼, 없으면 시스템 뒤로 키. 탭 루트에서는 화면 안 뒤로 버튼이 있을 때만 | 0.3 |
| tab | 하단 탭 중 무작위 하나. 탭마다 후보로 두지 않는다(합이 커져 깊이가 리셋된다) | 0.2 |
| doubleTap | 직전에 누른 버튼을 3번 연타 | 0.15 |
| backDuringLoad | 누르고 0.3초 안에 뒤로 | 0.15 |
| background | 홈 키 → 3초 → 앱 다시 열기 | 0.1 |
| restart | 강제 종료 → 다시 열기 | 0.05 |
| homeReset | 열린 화면을 닫고 홈 탭 | 0.05 |

## 점수

```
기본 = 종류별 가중치
       press는 하나당 min(1, 3 / 이 화면 누르기 수)       버튼이 많아도 누르기 합은 3까지
       × 1.5 링크, × 3 이번 실행에서 안 가 본 경로, × 1.5 더 깊은 경로
       ÷ (1 + 머문 스텝/2)                               오래 머물면 덜 누른다
       back·tab·homeReset은 × (1 + 머문 스텝/2)           오래 머물면 나간다
점수 = 기본 × 1/(1 + 이 화면에서 한 횟수)
           × 2   처음 보는 상태로 간 적이 있음
           × 3   이 행동 뒤 오류가 난 적이 있음
           × 0.2 반응 없음이 두 번 이상
```

점수에 비례해 하나를 뽑는다(mulberry32 시드 난수). 같은 시드·같은 앱 상태면 같은 순서다. 가중치·배수는 작성자 판단이며 실기기에서 돌려 보며 맞춘다.

- 비밀번호·PIN 경로(`noPressPathPattern`)는 누르지 않고 나가기만 한다.
- 행동이 연달아 3번 실패하면 멈춤으로 기록하고 앱을 재시작한다.
- 다른 앱(광고 등)이 앞에 뜨면 대상 앱으로 돌아와 이어 간다.

## 실행 단위

- 회차: 홈에서 시작해 최대 50스텝. 끝나면 홈으로 리셋하고 다음 회차.
- 실행: 시간 예산(기본 60분) 안에서 회차를 반복한다. 행동 통계는 회차 사이에 이어진다.
- 디바이스팜 점검이 도는 중이면 시작하지 않는다.

## 판정·기록

스텝마다 탐색 점검과 같은 probe로 오류·경고를 본다. 레이아웃 문제는 정확도가 낮아 경고로만 남긴다. 재시작·백그라운드 직후 빈 화면은 로딩으로 본다. 같은 오류는 실행 안에서 한 번만 센다.

`test-results/chaos/<runId>/run.json`에 스텝마다 상위 후보 점수·고른 행동·이동·새 상태 여부·오류를 남기고, 오류 스텝은 스크린샷을 남긴다. 웹 화면 「카오스」 탭에서 본다.

## 아직 없는 것

입력칸 경계값, 네트워크 끊김, 오류를 다시 내는 최단 경로로 줄이기.
